## 二、逐项：场景 + 造成的原因

### HG-SEC-202 — 设计 §0.4-A 例外表「4 表 11 列」+ `history` 例外归因错

**场景**：`[2/6]` 评审发现「4 个 drama strategy 表不可按参数重生成」（按 JSON 重生成会丢列 / 内容回归），
`[3/6]` 前的设计 v1.2 §0.4-A 需把这一例外登记成白名单。补记写作时把 4 个表统一描述为「11 列」，
并把原因归为「其 JSON 仍是旧 7–8 字段口径（列集落后产物）」。

**造成的原因**：
1. **归因取自「最省事的共同点」而非逐表复算**：4 表当时都表现为「重生成后与仓内产物不同」，
   补记直接把差异统一解释为「JSON 列集落后」；实际只有 3 个表是列口径问题、`history` 的 JSON 与产物**列集已同步（11/11）**。
2. **差异性质未分类**：`history` 重生成仍差 **212 行**，实测是**样式基座漂移**（`.tabs-row` / `.tabs-actions` /
   `.home-link` 等 CL005 基座），属「模板历史漂移」类，与「列集落后」是两种不同的 diff 性质。
3. **计数采用口头汇总**：4 表列数未逐表 `th`/`label` 计数，而是按当时「多数表 10 列 + history 略多」的印象写成统一「11 列」。

**影响**：不影响处置（4 表无论何种原因都按例外保持现状 + 手工同步 canonical 块，内容 0 丢失），
但使「按 JSON 重生成即回归」的表述不完全自洽（审计因此扣基线口径 1 分）。
**修法**：§0.4-A 改为分表列数（3×10 + `history` 11）+ `history` 归因改为「样式基座漂移（212 行）」。

### HG-SEC-203 — ops 回执 TC11/TC8 计数口径差

**场景**：`[4/6]` ops 自建 harness 报告 18 项判据，其中 TC11 报「4 表基线列 10 / HEAD 10」、
TC8 报「文档面（声明项）10 行」。

**造成的原因**：
1. **TC11 用集合差代替计数**：判据写作 `列标签集(基线) - 列标签集(HEAD) == ∅`（判「有无丢失」）。
   实现上取 `<th>` 文本 ∪ `label:` 值的**去重并集**，`history` 表存在同值项被并集吞掉 1 列 ⇒ 报 10 而非 11。
   根因是**为便利选的判据实现**与「列数」这一业务口径不对齐（判据语义正确 ≠ 计数口径正确）。
2. **TC8 用物理行代替逻辑行**：以 `git diff -U0` 的 `+/-` 物理行计（10），审计按「逻辑改动行」计（20 = 文案 9 + meta 11）。
   同一份 diff 两种合理口径，报告未写明所用口径 ⇒ 读者无法复算一致。

**影响**：无（「零丢失」「区间外未声明改动 0」两条实质结论双方独立一致）。
**修法**：报告已 §8 勘误（E1/E2）；后续 harness 纪律：**计数类判据须写明口径并逐项打印原始计数**。

### HG-SEC-204 — 设计 §7 A4 验收条款「他仓 `git status` 空」不可满足（且被审计误标来源）

**场景**：设计 v1.2 §7 验收表 A4 行要求「只读探针**不写他仓**（断言 `git -C ../script-miner status --short` 无新增）」。
`[5/6]` 审计执行该条款时该命令输出 ` M efficiency/workflow-prompt.md` ⇒ 判为「证据行不实」，
并在台账中记为「**ops 回执** A4」。

**造成的原因**：
1. **条款把「只读」表达成了「他仓工作树干净」**：探针只读是**本步行为**属性，而 `git status` 反映的是
   **他仓全体（含其他会话/他线并发）**状态 ⇒ 他仓只要有任何无关脏文件，条款即恒假（不可满足）。
   实测该脏文件 mtime `Sep 28 11:58`，早于本步核查（约 12:20），与本步无关。
2. **审计引用时把条款来源标成了 ops 回执**：该句原文位于设计 v1.2 §7 A4 行（`:386`），
   ops 回执（`documents/review/...ops-verify-v1.0-...md`）**无任何 `script-miner status` 断言**
   —— ops 侧 `grep -rn "script-miner status\|零写他仓" documents/ review-log.md TODO-handoff.md` 实证为空。

**影响**：不影响结论（「探针只读」经两条独立取证成立：探针源码零写操作扫描命中 0 + mtime 早于本步）。
**修法**：① 条款改为「探针**源码零写操作**扫描 + 目标文件 **mtime 取证**」；
② 审计台账中 204 的来源改为「设计 §7 A4 条款措辞」；③ 教训：**跨仓只读的判据不得以他仓工作树状态为断言**。

### HG-SEC-205 — `bf61484` 既有用例夹具 docstring 的环境前提与实测不符

**场景**：`[3/6]` dev 修改既有用例 `tests/test_templates.py::TestDocShowMd::test_doc_title_click_copy_path`
（原用例在旧实现下因「无条件 `showToast`」而恒绿 = 假成功断言）；为使成功分支可观测，注入
`navigator.clipboard.writeText` 可用桩，并在 docstring 写明前提：「headless Chrome 在 `file://` 下
`writeText` 抛 `NotAllowedError` **且 `execCommand('copy')` 返回 false**」。

**造成的原因**：
1. **结论由单一观测面过度推广**：该「execCommand 返回 false」的判断来自「JS 直调（**无用户激活**）」观测；
   而本批 canonical 设计的核心分野恰是**有无用户激活**——实测 Selenium 可信点击（**有激活**）的 headless `file://` 下
   `execCommand('copy')` **返回 True**。夹具注释把「无激活分支」的观测写成了环境通性。
2. **夹具不承重使错误前提未被测试暴露**：有桩/无桩均绿（真实复制在 `file://`+有激活下本可用），
   因此错误注释没有任何测试反例去纠正它。

**影响**：注释误导后续读者（可能误判「headless 永远无法真复制」）；夹具本身无害、断言未削弱。
**修法**：注释改为「`writeText` 在 headless `file://` 下 reject；`execCommand('copy')` 仅在**无用户激活**时返回 false
（**有激活时返回 True**）⇒ 本桩仅用于稳定观测成功分支的 toast 文案」。

### HG-SEC-206 — 判据恒真/误报（审计 2 例 + ops 3 轮）

**场景**：两侧 harness 均出现「判据本身错」的情形：
- 审计侧：① 4 个 strategy 表初版按静态 `<table>` 解析（产物表由 JS 注入 ⇒ 0 列 0 行「平凡 PASS」）；
  ② 全量重生成比对初版把 `countries-table.md` / `provinces-table.md` 等**数据源说明 md** 当 doc 源，
  与 table 产物**同名碰撞** ⇒ 误报 2 例 DIFF（sha256 核实实为逐字节相同）。
- ops 侧（本批 3 轮，已记于核查报告 §4）：关键词分类漏 `<script>` 区间判定 / TC11 硬编码列名 /
  `§3.3` 与 `83.3%` 误命中版本正则 / 不容忍 meta 时间戳 / 同一改动的删除侧未对称归类。

**造成的原因**：
1. **判据先于被测形态设计**：解析方式假设了「静态 HTML 表格」「文件名唯一」等前提，而这些前提未与产物实际形态
   （JS 注入、md 与产物同名）对齐；「0 命中也算 PASS」的判据天然容纳了恒真。
2. **缺少「恒真项识别 + 反证」环节**：首轮判据跑绿即被当作通过，未追问「本判据在**修前**是否也会绿」；
   ops 侧的补救方式是**把同一 harness 指向基线副本（3 PASS / 7 FAIL）**，审计侧靠变异测试（3 态，M3 指名行号）。

**影响**：无（两侧均在提交前自证并留档，未污染结论）。
**修法**：本批已确立纪律并沿用——① 每轮判据改动**只改判据、不改被测物**并留复跑记录；
② 报告必须含 **≥1 项反证（判据指向基线应转红 / 变异测试）**；③ 计数类判据打印原始明细；
④ 文件名碰撞类必须用 **sha256** 复核而非仅比对存在性。

## 三、共性根因（5 项归三类）

| 类 | 特征 | 命中项 | 预防准则 |
|:--|:--|:--|:--|
| A. 观测面过度推广 | 由单分支/单次观测写成通性（环境前提、原因归属） | 202、205 | 结论须标注观测条件（有/无用户激活、单表 vs 全表），并做反例探针 |
| B. 判据口径与业务口径不一致 | 集合差 vs 计数、物理行 vs 逻辑行、他仓状态 vs 本步行为 | 203、204 | 报告写明口径 + 打印原始计数；只读性判据只断言**本步行为** |
| C. 判据未自检（恒真/误报） | 假设形态、名字碰撞、正则误命中 | 206（含 ops 3 轮） | 必做反证/变异；碰撞用 sha256 复核 |

**一句话**：本批 5 项 errata **无一涉及产品行为**（修法本身 18/18 + 95/100 双 PASS），
全部是**文档/判据的表述与口径问题**；其价值在于把「结论由判据产生」这件事显式化 ——
**判据错与产品错同等重要，且只能靠反证发现**。

## 四、不修正的后果（逐项 + 系统级 + 优先级建议）

> 口径：只描述**不修**会发生什么（含「下批/下一位读者会怎么被带偏」的具体链路），不含产品行为影响——
> 5 项均不动代码，产品面已双 PASS（ops 18/18 + 审计 95/100）。

### 202 — 设计 §0.4-A 措辞 + `history` 归因不修

| 面 | 不修的后果（链路） |
|:--|:--|
| 决策误导 | 后续批次读 §0.4-A 会得到两条错事实：「4 表都是 11 列」「4 表不可重生成皆因 JSON 列集落后」。若据此**去补 drama 表 JSON 列集**以求「可重生成」——改的是数据面，**212 行样式基座漂移仍在** ⇒ 得到「列补完了、diff 还差 200+ 行」的二次困惑，且已白改数据 |
| 漏根因 | `history` 的真因（`.tabs-row/.tabs-actions/.home-link` 等 CL005 基座漂移）不被登记 ⇒ 同一漂移若影响其它产物，没有线索可循（本批正是靠基线笔才把它与「列集落后」区分开） |
| 自洽性 | 「按 JSON 重生成即回归」的表述无法自洽，审计每轮都要重算这 212 行（本批已扣 1 分） |
| 累积成本 | 低成本可修（改 2 处措辞）；不修则每轮涉及 drama 表的批次都要重新论证一遍 |

### 203 — ops 回执计数口径不修

| 面 | 不修的后果（链路） |
|:--|:--|
| 不可复算 | 后续审计按报告数字复算会得到不一致值（本批已实际发生：审计复算出 history 11 而非 10、逻辑行 20 而非 10）⇒ 每轮多一次「谁的数字对」的来回 |
| 数字扩散 | 若这组数字被当作**历史基线**写进下一批设计（如「4 表 10 列」「文档面 10 行」），错误被固化 |
| 判据退化 | 口径不写明 ⇒ 下批仍会用「集合差」代替计数（判「有无丢失」是对的，但报数就错），同类 errata 复发 |

### 204 — 设计 §7 A4 条款（+ 审计误标来源）不修

| 面 | 不修的后果（链路） |
|:--|:--|
| 验收失效 | 条款「他仓 `git status` 无新增」恒假 ⇒ 每次跑到 A4 都要人工解释「为什么非空」，久而久之形成**制度化豁免**；一旦形成豁免，**真正的越界写操作**也可能被淹在他仓脏文件噪音里（本次若探针真写了他仓，反而看不出来） |
| 误导检索 | 台账把来源标成「ops 回执」，后人去 ops 回执里找这句断言**永远找不到**（grep 已实证不存在）⇒ 白耗一轮检索，甚至误判「ops 回执被篡改」 |
| 正确判据被埋 | 真正可用的判据（探针**源码零写操作**扫描 + 目标文件 **mtime 取证**）没被写成条款 ⇒ 下批跨仓只读验收仍会照抄这条不可满足的版本 |
| 累积成本 | 改 1 行条款 + 改 1 处来源标注即可；不修则每次跨仓核查都重复踩 |

### 205 — `bf61484` 夹具 docstring 不修

| 面 | 不修的后果（链路） |
|:--|:--|
| **同类缺陷复发** | 注释断言「`file://` 下 `execCommand('copy')` 返回 false」被下一位开发者当作环境公理 ⇒ 他会认为「非安全/headless 下真复制不可能」，于是**只断言文案**、不写真实复制断言 —— 这正是本批要根治的**假成功断言**老路的翻版 |
| 排障走偏 | 移动端/其它环境排查时，会把真缺陷误判为「环境限制」而放过（本批原始 bug 的成因就是「把失败当环境问题」） |
| 测试退化 | 夹具本身不承重（有桩/无桩均绿）已说明它与真实路径脱钩；注释再错 ⇒ 后续维护者可能删掉它或误改断言 |
| 累积成本 | 改 3 行注释即可；不修则风险随「谁来读这份测试」而放大 |

### 206 — 判据未自检（恒真/误报）不修

| 面 | 不修的后果（链路） |
|:--|:--|
| **假 PASS（唯一高危路径）** | 恒真判据会给出「通过」而实际未验证：① 若本批首轮的「静态 `<table>` 解析 0 列 0 行」被当作结论，4 表的例外判定就没有依据；② ops 首轮若未发现「删除侧未归类」，产物面「零未声明改动」的断言会漏掉一类改动 ⇒ **可能带真缺陷过审发布** |
| 常驻守卫永久失效 | 最危险之处：把恒真判据**固化进 `tests/`**（本批新增 12 条常驻守卫）后，它会长期报绿而无人察觉 —— 与「假成功断言」是同一类病，只是从产品层搬到了测试层 |
| 返工成本 | 误报（同名碰撞 2 例、ops 3 轮）每轮都要重跑重判；本批两侧合计约 5 轮返工时间 |
| 累积成本 | 修法成本近零（**纪律**而非代码）：报告必含反证/变异 + 计数打印口径 + 碰撞用 sha256 复核 |

### 系统级：整批不修会怎样

1. **errata 台账长期悬挂**：5 项都属「已登记未闭环」，下一批开题复核时需重新判定其状态，形成固定开销。
2. **同类场景重踩**：这 5 项分别对应 4 个会复现的场景 —— ① drama 表类「产物/数据口径不一致」② 跨仓只读验收
   ③ headless 剪贴板类测试 ④ 任何 harness 判据 —— 不修则每类都会再出一次同形 errata。
3. **最需固化的是 206**：它是唯一能**产出假 PASS** 的类型（其它 4 项只会误导人或浪费回合，不会让缺陷溜过审）。
   建议把一条准则落规范层（skill/协议，**Ask First**）：「任何核查/审计报告须含 ≥1 项反证或变异证据；
   计数类判据须打印原始计数并写明口径；名字碰撞类比对须用 sha256 复核」。

### 优先级建议（按后果严重度，非按发现顺序）

| 序 | 项 | 后果等级 | 理由 | 建议修法成本 |
|:--|:--|:--|:--|:--|
| 1 | **206** | 高 | 唯一可产出**假 PASS**（含常驻守卫永久失效） | 纪律/规范层（若落 skill 需批准） |
| 2 | **205** | 中高 | 直接诱发**同类缺陷复发**（假成功断言的老路） | 改 3 行注释 |
| 3 | **204** | 中 | 验收条款恒假 ⇒ 制度化豁免 ⇒ 真越界被淹没 | 改 1 行条款 + 1 处来源标注 |
| 4 | **202** | 中 | 误导决策方向（可能白改数据面）+ 掩盖真根因 | 改 2 处措辞 |
| 5 | **203** | 低 | 只影响可复算性/信任，本批已就地勘误 | 纪律固化（已部分完成） |
